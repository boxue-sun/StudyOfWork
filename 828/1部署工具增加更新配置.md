### 你解决的问题的本质

**一句话**：设备模块读配置文件初始化，但配置文件里是默认值，现场实际参数在工参表里。你加了一个"启动时同步"的中间层。

```
工参表（现场真实参数）
    ↓ WriteBackFromCommParam()  ← 你加的这一层
device.yaml（被覆盖成真实值）
    ↓ LoadConfig()
设备模块（用真实参数初始化）
```

## 怎么把这次经验变成自己的

### 1. 不要只记"改了什么文件"，要理解"为什么这么设计"

你需要能回答这几个问题（能回答就说明你真懂了）：

- **为什么不在设备模块里直接读工参表？** → 因为设备模块是厂商提供的插件，不应该跟工参表耦合。工参同步是平台层的职责，放在 Component 层做。
- **为什么在 `LoadConfig` 之前调用？** → 因为 `LoadConfig` 读的就是 YAML，必须先覆盖再读。
- **为什么 `peerAddresslist` 只改第一个？** → 因为第一个是直连信号机的对端，第二个是云控平台地址，不需要从工参表覆盖。

### 2. 理解整体架构

你做的不是孤立的一个功能，而是一个**架构模式**：

```
RSU 模块   → WriteBackFromCommParam() → standard_rsu.yaml     ✅ 已有
信号机模块 → WriteBackFromCommParam() → device.yaml            ✅ 你做的
摄像头模块 → （未来可能也需要）                                   ❌ 待做
```

这就是"工参同步"的统一设计模式，每个设备模块都一样：读工参 → 写 YAML → 设备读 YAML。

### 3. 简历上怎么写

不要写"用 AI 改了 3 个文件"，要写**你解决了什么问题**：

> **信号机工参同步功能开发**
>
> - 问题：信号机模块启动时使用配置文件中的默认 IP/端口，无法获取现场运维工参表中的实际设备地址，导致部署后无法与信号机正常通信
> - 方案：参照 RSU 模块已有的工参同步模式，在信号机 Component 的 Init 流程中增加工参同步步骤，启动时从全局工参表读取信号机参数（serverIp/serverPort/peerIp/peerPort），覆盖写入设备配置文件后再初始化设备
> - 实现：新增 TrafficLightParamConfiger 数据结构并集成到全局工参解析模块，实现 WriteBackFromCommParam 方法完成配置回写
> - 验证：通过构造测试工参数据，验证配置文件被正确覆盖，设备使用实际参数初始化

### 4. 下次怎么减少对我的依赖

- **先自己读懂 RSU 的 `WriteBackFromCommParam()`**，理解每一行在干嘛，然后再写信号机的版本
- **改之前先画数据流**：数据从哪来、经过什么、到哪去。画清楚了代码自然就写出来了
- **编译报错先自己看**：这次的 `operator<` 错误，关键信息就是 `CameraEventParamConfiger` 没有 `<` 运算符，定位到 `std::tie` 那一行就能找到原因
