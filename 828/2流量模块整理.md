## 一、项目背景：我做的功能是什么

### 1.1 系统原本在干什么

traffic_flow 模块的职责：**统计路口的交通流量**（车流量、排队长度、占有率等）。

原来的数据流只有一条：

```
感知数据(摄像头/雷达检测的车辆) 
    → DDS订阅 → 阻塞队列 → detect()主线程统计 → 发布结果
```

统计方式是**固定时间周期**：不管红绿灯，每5秒出一次流量数据。

### 1.2 为什么要加信号灯数据

**业务需求**：交通流量按信号灯周期统计更有意义。
比如"这个绿灯周期内通过了多少车"比"5秒内过了多少车"更能反映路口通行效率。

所以新增了第二条数据流：

```
信号灯数据(信号机的红绿灯状态) 
    → DDS订阅 → 解析 → SignalPhaseManager缓存 
    → detect()检测相位边界 → 触发统计
```

### 1.3 数据从哪来

信号机硬件 → (UDP二进制, GA/T 1743协议) → **TLP模块**(翻译成JSON) → DDS → 我的模块

我只需要关心"DDS给我的JSON长什么样"，不用管TLP怎么解析二进制。

### 任务2：PartId 枚举新增

**文件**：`src/plugin/traffic_flow_service_impl.h`

```cpp
enum class PartId : uint8_t {
    RSM_JSON_SUB = 0,
    TRAFFIC_FLOW_JSON_PUB = 1,
    SIGNAL_JSON_SUB = 3,      // ← 新增
    ...
};
```

**为什么用 `enum class` 而不是普通 `enum`**：
1. **强类型**：不会隐式转成 int，避免误用
2. **作用域限制**：`PartId::SIGNAL_JSON_SUB`，不会污染命名空间
3. **指定底层类型** `: uint8_t`：跟 DDS 传来的 `uint8_t id` 对齐

**面试考点**：`enum` vs `enum class` 的区别（必考题！）

### 任务3：on_data_available() 新增 case 分支

**文件**：`src/plugin/traffic_flow_service_impl.cpp`

**做了什么**：DDS 收到消息后回调这个函数，根据 `id` 分发：

```cpp
switch (message_type) {
    case PartId::RSM_JSON_SUB: { ... }
    case PartId::SIGNAL_JSON_SUB: {
        std::string signal_json = std::string(
            static_cast<char*>(fusion_message->body), fusion_message->body_size);
        auto phases = traffic_flow::parse_signal_json(signal_json);
        traffic_flow::SignalPhaseManager::get_instance().update(phases);

**关键细节**：
- `fusion_message->body` 是 `void*`，需要 `static_cast` 转成 `char*` 再构造 string
- `std::string(ptr, size)` 这种构造方式能处理带 `\0` 的二进制数据，比 `char*` 直接构造更安全

**面试考点**：`void*` 的使用与转换、`static_cast` vs `reinterpret_cast`

### 任务4：JSON 解析函数

**新建文件**：`src/common/signal_phase_data.h` / `.cpp`

**核心思想：把非结构化的 JSON 变成强类型的结构体**

```cpp
// 1. 灯态枚举：把魔法数字变成有意义的名字
enum class SignalLightState : uint8_t {
    RED = 3,
    PROTECTED_GREEN = 6,
    YELLOW = 7,
    ...
};

// 2. 数据结构：一个方向的完整灯态信息
struct SignalPhaseData {
    DirectionCode direction;
    SignalLightState light;
    int32_t time_remaining;
    uint64_t timestamp;
};

// 3. 映射函数：协议里的phaseId → 业务里的方向
inline DirectionCode phase_id_to_direction(int32_t phase_id) {
    switch (phase_id) {
        case 2:  return DirectionCode::NORTH;   // 北直行
        case 10: return DirectionCode::EAST;
        case 18: return DirectionCode::SOUTH;
        case 26: return DirectionCode::WEST;
        default: return DirectionCode::DEFAULT;
    }
}
```

**解析函数的防御性编程**（每一层都做校验）：
```cpp
std::vector<SignalPhaseData> parse_signal_json(const std::string& json_str) {
    // 防御1: 空输入
    if (json_str.empty()) return result;
    
    // 防御2: JSON格式错误，用try-catch兜底
    try {
        j = nlohmann::json::parse(json_str);
    } catch (const std::exception& e) { return result; }
    
    // 防御3: 字段缺失，逐层判断
    if (!j.contains("intersections") || ...) return result;
    
    // 防御4: 用 value() 提供默认值，避免抛异常
    int32_t phase_id = phase.value("phaseId", 0);
}
```

**面试考点**：
- 防御性编程思想
- 异常处理什么时候用、怎么用
- "魔法数字"的危害与枚举的意义

### 任务5：SignalPhaseManager（最核心，面试重点讲）

**新建文件**：`src/common/signal_phase_manager.h` / `.cpp`

**这个类解决两个问题**：
1. **跨线程共享状态**：DDS回调线程写入，detect()线程读取
2. **检测状态变化**：识别"绿→红"的相位边界

```cpp
class SignalPhaseManager final : public cybertron::base::Singleton<SignalPhaseManager> {
    friend class cybertron::base::Singleton<SignalPhaseManager>;

public:
    void update(const std::vector<SignalPhaseData>& phases);      // 写
    bool check_phase_boundary(DirectionCode direction);            // 读
    SignalLightState get_light_state(DirectionCode direction);

private:
    SignalPhaseManager() = default;   // 私有！只能通过单例访问
    std::mutex _mtx;                   // 保证线程安全
    std::unordered_map<DirectionCode, SignalLightState> _current_states;
    std::unordered_map<DirectionCode, SignalLightState> _previous_states;
    std::unordered_map<DirectionCode, bool> _boundary_triggered;
};
```

**为什么是单例？**
- 全局只需要一份灯态状态
- 两个线程要访问**同一个**对象才能通信
- 项目里已有 `Singleton` 模板基类，直接继承（代码复用）

**为什么构造函数要私有 + friend？**
- 构造函数私有：外面不能 `new` 或 `SignalPhaseManager m`，强制走单例
- `friend Singleton<...>`：让单例基类能访问私有构造函数

**核心逻辑——边界检测**：
```cpp
void SignalPhaseManager::update(const std::vector<SignalPhaseData>& phases) {
    std::lock_guard<std::mutex> lock(_mtx);   // RAII 加锁
    for (const auto& phase : phases) {
        _previous_states[dir] = _current_states[dir];  // 保存旧状态
        _current_states[dir] = phase.light;             // 更新新状态
        // 绿→红 = 一个周期结束
        if (_previous_states[dir] == SignalLightState::PROTECTED_GREEN &&
            phase.light == SignalLightState::RED) {
            _boundary_triggered[dir] = true;
        }
    }
}
```

**为什么用 `lock_guard` 而不是手动 `lock()/unlock()`？**
- RAII 思想：构造时加锁，析构时自动解锁
- 即使中途抛异常或 return，锁也会被正确释放
- 不会忘记解锁导致死锁

**面试考点（高频！）**：
- 单例模式的实现（饿汉/懒汉/线程安全）
- `lock_guard` vs `unique_lock` 的区别
- RAII 是什么，为什么重要
- 多线程共享数据如何保证安全
- `unordered_map` vs `map` 的选择（哈希表，O(1)查找）

## 三、这个项目涉及的架构知识（面试吹点）

### 3.1 DDS 发布-订阅模式（Pub-Sub）

```
发布者(Publisher) ──发到──> Topic(主题) <──订阅── 订阅者(Subscriber)
```

- 发布者和订阅者**完全解耦**，互不知道对方存在
- 只通过 Topic（话题）关联
- `domain_id` 相当于"域"，同一个域内才能互相通信
- 数据到达时，框架自动回调 `on_data_available()`

**类比**：微信公众号。你关注了公众号（订阅），作者发文章（发布），你收到推送（回调），但你和作者互相不认识。

### 3.2 生产者-消费者模式（BlockingQueue）

现有 RSM 数据流用了这个模式：

```
on_data_available(生产者) → BlockingQueue → detect()线程(消费者)
```

**为什么要用队列解耦？**
- 接收速度和处理速度可能不匹配
- 队列做缓冲，避免丢数据
- 两个线程各司其职，互不阻塞

### 3.3 插件化架构

`FusionPlugin.h` 定义了一套插件接口规范：
```
每个插件编译成 .so 动态库
主程序 FusionService 运行时加载插件
插件实现 Init/OnDataAvailable/OnPublish 等回调
```

**好处**：主程序不用重新编译，插件可以独立开发、独立升级。

**面试考点**：动态库加载（`dlopen`/`dlsym`）、回调函数、接口与实现分离

## 四、面试怎么讲这个项目（话术模板）

### Q1: 介绍一下你做的项目

> 我在一个智能交通项目中负责信号灯数据接入模块。这个系统通过 DDS 中间件做模块间通信，原来只有摄像头/雷达的感知数据流，按固定5秒周期统计路口流量。我的任务是新增一路信号灯数据流，让系统能按红绿灯周期统计流量——比如一个绿灯周期内通过了多少车。
> 
> 具体做了三块：
> 1. **配置层**：新增 DDS 订阅配置，接入信号灯 Topic
> 2. **数据层**：写解析函数，把信号灯 JSON 转成强类型结构体，做了完整的防御性校验
> 3. **状态层**：实现了一个线程安全的 SignalPhaseManager 单例，缓存4个方向的灯态，检测绿→红的相位边界，触发对应方向的流量统计

### Q2: 遇到了什么难点？

> **多线程数据竞争**。信号灯数据由 DDS 回调线程写入，而流量统计在另一个 detect() 线程读取，两个线程访问同一个单例对象。我用 `std::mutex` + `lock_guard` 保护共享状态，用 RAII 保证锁的正确释放。

### Q3: 为什么用单例模式？

> 因为灯态状态全局只有一份，且需要被两个线程共享。单例保证全局唯一访问点。我用的是项目里现成的模板单例基类，通过 `std::call_once` 保证线程安全的初始化，构造函数私有防止外部实例化。

### Q4: 怎么保证解析的健壮性？

> 外部数据不可信，我在每一层都做了校验：空输入检查、JSON 解析用 try-catch 捕获格式错误、字段访问先判断存在性、用 `value(key, default)` 提供默认值。即使信号机数据异常，模块也只是跳过这帧，不会崩溃。
