## 简历第 1 条：ROS 2 节点架构

> 按业务拆分导览状态机、语音播报、问答、访客检测、语音输入 5 个节点，通过 Topic 与 Action 完成节点间状态传递与导航目标下发；使用 Launch、YAML 管理节点启动、话题映射与展点配置。

### 1.1 五个节点怎么拆的（业务边界）
| 节点 | 文件 | 职责 |
|---|---|---|
| 导览状态机 | `tour_node.py` | 主控：状态流转、下发导航目标、发讲解词 |
| 语音播报 | `tts_node.py` | 订阅讲解文本，pyttsx3 本地合成 |
| 问答 | `qa_node.py` | 关键词规则匹配回答 |
| 访客检测 | `visitor_detector.py` | 迎宾触发（fake 距离 / 摄像头红色） |
| 语音输入 | `voice_input_sim.py` | 模拟提问（无真实麦克风） |

拆分原则：**一个节点一个业务职责**，节点之间只靠话题/Action 通信，互不 import 业务逻辑——改一个节点不影响其他节点。

### 1.2 节点间通信：Topic 与 Action 各管什么
- **Topic（持续、单向、轻量）**：状态与事件传递
  - `/tour_guide/state`：tour_node 广播当前状态（各节点据此决定要不要干活）
  - `/tour_guide/visitor_detected`：访客检测 → 状态机（迎宾事件）
  - `/tour_guide/speech`：状态机 → TTS（讲解词）
  - `/tour_guide/question`：模拟提问 → 问答节点/状态机
- **Action（长任务、有状态、可取消）**：导航目标下发
  - `/navigate_to_pose`：tour_node 是 Client，Nav2 是 Server
  - 为什么导航不用 Topic：导航要持续几十秒，需要"接受/进行中/反馈/成功/取消/失败"全生命周期状态；**目标被接受 ≠ 到达**，必须等最终结果才能进讲解。

### 1.3 Launch 与 YAML 管什么
- **Launch**：`demo.launch.py` 用 IncludeLaunchDescription 嵌套三套 launch（robot/navigation/tour_guide）并行拉起；`run_all.sh` 是 shell 串行 + sleep + 日志重定向的低配虚拟机稳定版。**两者是替代方案不是配合关系**。
- **YAML**：
  - `tour_points.yaml`：展点坐标、讲解词、问答提示、循环/等待开关
  - `qa_rules.yaml`：问答关键词与答案
  - `nav2_params.yaml`：导航栈全部参数
  - `gz_bridge.yaml`：ROS↔Gazebo 话题映射翻译表
- 面试话术："**配置数据与代码逻辑分离**，加展点、改讲解词、调导航参数都不用改代码。"

## 简历第 2 条：定位与导航

> 集成 Nav2 导航栈，配置 AMCL 完成已知地图定位、NavFn（Dijkstra）全局路径规划与 DWB 局部轨迹跟踪；配置全局/局部代价地图（障碍层+膨胀层）实现避障，通过 Lifecycle 节点编排导航栈激活顺序。

### 2.1 AMCL 怎么用雷达定位（今天的疑问）
AMCL = 自适应蒙特卡洛定位（粒子滤波），5 步：
1. **撒粒子**：地图上撒 100~400 个"机器人可能在这"的猜测（`min_particles:100, max_particles:400`）；
2. **模拟扫描**：每个粒子按地图算"站在这应该扫到的墙距离"；
3. **比对打分**：与真实 `/scan` 对比，越吻合权重越高；
4. **重采样**：高权重粒子附近多撒，低的淘汰；
5. **收敛**：粒子群收缩到真实位置，输出 map 下位姿，并发布 map→odom 修正（`tf_broadcast: true`）。

一句话："如果我站在这，雷达应该看到这些墙；真实雷达也看到了，那我就真在这。"
本项目 `set_initial_pose: true`，初始 (0,-3.5) 与出生点一致，不用手动点 2D Pose Estimate。

### 2.2 NavFn 全局规划（注意：是 Dijkstra 不是 A*）
- 插件 `nav2_navfn_planner::NavfnPlanner`，参数 `use_astar: false` → **当前走 Dijkstra 分支**。
- 在全局代价地图上搜索"当前位置 → 目标点"的路径。
- 展点**顺序**是 tour_points.yaml 预设的，但两点之间**具体走哪条路**由规划器算——"路线顺序预设"与"自主规划路径"同时成立。

### 2.3 DWB 局部控制
- 插件 `dwb_core::DWBLocalPlanner`：采样多组速度（vx_samples=10, vy_samples=1, vtheta_samples=10）→ 预测短时轨迹 → 按碰撞风险/偏离全局路径/距目标打分 → 输出最优 /cmd_vel。
- 差速车不能横移，所以 vy_samples=1，不浪费算力。
- 控制频率 10Hz，max_vel_x=0.26 m/s。

### 2.4 代价地图：障碍层 + 膨胀层
- **全局代价地图**：给全局规划用，覆盖整张地图。
- **局部代价地图**：跟随机器人的 3×3m 滑动窗口，给 DWB 用。
- **obstacle_layer（障碍层）**：把 /scan 实时扫到的障碍写入/清除。
- **inflation_layer（膨胀层）**：在障碍周围加"代价渐变区"，让路径离墙留安全距离（`robot_radius:0.22, inflation_radius:0.55`）。
- 静态地图只知道"哪是墙"，代价地图把"离墙多近有风险"也量化了——这就是避障的实现。

### 2.5 Lifecycle 节点编排激活顺序
- Nav2 各组件（map_server、amcl、controller_server、planner_server、behavior_server、velocity_smoother、bt_navigator）都是 **Lifecycle 生命周期节点**，要经过 configure → activate 才能工作。
- 本项目用 `bringup_nav.py` 按顺序逐个调用生命周期服务激活，**失败自动重试**，全部 ACTIVE 才放行导览（日志出现 ALL ACTIVE）。
- 面试话术："导航栈不是启动就能用，必须显式激活；我做了激活重试和失败拦截，避免导航没就绪就开始发目标。"

### 2.6 地图：图片、障碍物、origin（今天的疑问）
- 地图 = png 图片 + yaml 元数据。白=可通行，黑=障碍，灰=未知。
- **障碍物是提前画在图上的**：由 `tools/gen_world_and_map.py` 按已知几何生成（效果等价于 SLAM 扫出来的，但当前不是边走边建图）。
- `tour_hall.yaml`：`resolution: 0.05`（1 像素=5cm），`origin: [-7.2, -5.2, 0]`（图片左下角像素对应的世界坐标）。
- **origin 的作用**：把像素翻译成世界坐标：`world_x = origin_x + pixel_x × resolution`。
- origin 标准流程是建图时自动记录的；本项目是配合仿真世界手工对齐设计的。三维 SDF 世界与二维地图**共用同一套墙/展台几何**，保证对齐。

## 简历第 3 条：导航与导览调度

> 通过 ROS 2 Action 下发导航目标并监听结果回调，使用有限状态机（5Hz 定时轮询）串联迎宾、导航、讲解、问答与巡游切换，导航失败时跳过当前展点继续巡游。

### 3.1 Action 下发与结果回调（tour_node 实现）
```
send_goal_async(goal, feedback_callback)   # 下发目标，注册过程反馈回调
  → _goal_response_cb                      # 目标是否被接受
  → get_result_async()
  → _goal_result_cb                        # 最终结果：成功→讲解，失败→跳过
```
- 全程**异步回调**，不阻塞状态机主循环。
- `goal.pose.header.frame_id = "map"`：目标点必须声明在 map 坐标系。
- yaw 转四元数：`z=sin(yaw/2), w=cos(yaw/2)`（绕 z 轴旋转）。

### 3.2 5Hz 定时轮询（之前确认过的正确理解）
- `create_timer(0.2, self._loop)`：**定时器只负责每 0.2s 触发一次 _loop 回调**，不是"唤醒整个节点"。
- `_loop` = 轮询当前状态、按条件推进状态机，是状态稳定前进的**主节奏**。
- 状态更新有**两条路**：
  1. _loop 定时轮询（主节奏，保证稳定推进）；
  2. 订阅回调（外部事件到达直接改状态，如收到迎宾事件、暂停指令）。
- 状态流：`INIT → WAIT_VISITOR → NAVIGATE → GUIDE → QA → NEXT →（有下一站回 NAVIGATE）→ FINISH`。

### 3.3 导航失败跳过展点
- Action 最终结果为失败/中止时：播报异常提示 → 展点索引 +1 → 继续下一站。
- 设计意图：**单点故障不阻塞整轮巡游**。
- 面试注意：验收要看每站结果，不能把"状态机走到 FINISH"当成全部导航成功。

### 3.4 导航完整链路 + 具体坐标例子（今天要求补的）
设定：机器人在接待台 (0,-3.5)，目标党史长廊 (-4.5,3.0)。

| 步骤 | 动作 | 数字 |
|---|---|---|
| ① | tour_points.yaml 配置展点 | 目标 = map (-4.5, 3.0) |
| ② | tour_node 填 goal，frame_id="map" | 发给 Nav2 |
| ③ | AMCL 雷达匹配地图 → 机器人 map 位置 | 当前 (0, -3.5) |
| ③b | TF 缝合 map→odom + odom→base_link | 得连续位姿 |
| ④ | NavFn 在全局代价地图规划 | (0,-3.5)→(-1.5,0)→(-3,1.5)→(-4.5,3.0) |
| ⑤ | DWB 采样打分输出速度 | /cmd_vel: v=0.2m/s, ω=0.1rad/s |
| ⑥ | 桥接 → Gazebo DiffDrive | 轮子转，车前进 |
| ⑦ | 轮转 → 里程计发 /odom | odom 位姿 (0.1,-3.5)（相对起点） |
| ⑧ | 循环③~⑦，AMCL 持续纠偏 | 位姿逼近 (-4.5,3.0) |
| ⑨ | 到达容差内，Action 返回 SUCCEEDED | 进入讲解 |

关键：⑦ 里 odom 只知道"相对起点走了 0.1m"——**odom 管"走了多远"，AMCL 管"在世界哪里"**。

## 简历第 4 条：建模与仿真

> 编写 URDF/Xacro 描述差速机器人模型，维护 map→odom→base_link→传感器的 TF2 坐标树；在 Gazebo Harmonic 搭建仿真环境，通过 ros_gz_bridge 桥接激光雷达与里程计话题。

### 4.1 URDF/Xacro（之前问过：开源还是 AI 生成？）
- 基于**开源差速车模板改造**（akhiljithvg/Autonomous-Navigation-Robot），不是纯 AI 生成。
- URDF 用 XML 描述：link（部件）、joint（连接）、visual（外观）、collision（碰撞）、inertial（质量惯量）。
- `robot.urdf` 含 Xacro 宏，启动时先 xacro 展开；`robot_state_publisher` 根据 URDF + joint_states 发布**结构内部 TF**（base_link→laser_frame 等）。
- `robot.gazebo` 挂插件：DiffDrive（收 cmd_vel 驱动轮子）、OdometryPublisher（发 /odom 和 odom→base_link，20Hz）、JointStatePublisher、gpu_lidar、IMU。

### 4.2 三层坐标系 map / odom / base_link（今天的核心，反复追问）

| 坐标系 | 本质 | 原点 | 会动吗 | 谁发布 |
|---|---|---|---|---|
| map | 世界地图坐标（全局绝对） | 地图固定点 | 不动 | AMCL 发布 map→odom |
| odom | 里程计参考系 | **机器人启动位置**，钉死 | 原点不动，但累积漂移 | Gazebo OdometryPublisher |
| base_link | 机器人本体 | 车体中心 | **跟车走、跟车转** | 里程计发布 odom→base_link |

**今天纠正的两个误区：**
- ❌ "odom 是轮子" → ✅ **轮子是测量工具（尺子），odom 是用轮子积分建立的参考系**。odom = odometry（里程计），读"欧多米"。
- ❌ "轮子在车上，所以 odom=base_link" → ✅ 两者是**不同参考系**：base_link 贴在车上、朝向跟车转；odom 钉在起点、朝向固定。机器人原地转 90°：base_link 跟着转，odom 纹丝不动——所以必须用 TF 描述二者关系。

**/odom 话题发的是什么**：机器人（base_link）在 odom 坐标系下的位姿 = "相对启动点走了多远、转了多少"。

### 4.3 导航用 map，为什么还要 TF 转 odom/base_link？（今天最关键的疑问）
"机器人在 map 下的连续位姿"是 **TF 树缝出来的**，两种定位源互补：

| 来源 | 发布 | 频率 | 优点 | 缺点 |
|---|---|---|---|---|
| 轮里程计 | odom→base_link | 高频 20Hz | 连续平滑 | 累积漂移 |
| AMCL | map→odom | 低频 | 绝对不漂移 | 更新慢、不连续 |

```
map→base_link = map→odom (AMCL 纠偏) ⊕ odom→base_link (里程计平滑)
```

只用 AMCL → 卡顿；只用 odom → 越走越偏。比喻：**odom=计步器（短期准长期漂），AMCL=GPS（偶尔绝对纠偏），TF 把两者融合**。

面试话术："导航目标用 map 坐标，但位姿靠 TF 链 map→odom→base_link 缝合：里程计保证高频平滑，AMCL 低频修正漂移，缺一不可。"

### 4.4 坐标在项目里用在哪？导航用哪个坐标？（今天的疑问）
四处用坐标，**导航全程只认 map**：
1. `maps/tour_hall.yaml`：origin/resolution，像素↔世界换算；
2. `tour_points.yaml`：5 个展点 x/y/yaw，全是 map 坐标；
3. `tour_node._point_pose()`：`frame_id = "map"` 填进 goal；
4. `nav2_params.yaml` AMCL `initial_pose: (0,-3.5)`。

**为什么目标必须用 map 不用 odom**：map 是绝对位置不漂移；odom 相对起点、会漂移，走几圈就偏。

### 4.5 Gazebo Harmonic 与 ros_gz_bridge（之前问过：发布订阅在哪？）
- Gazebo 用 gz-transport，ROS 2 用 DDS，**两套消息系统语言不通**。
- `parameter_bridge` 是 **ros_gz_bridge 包里的现成节点**（不是我们写的），按 `gz_bridge.yaml` 这张"翻译表"逐条转换。
- 发布/订阅不在我们代码里，在**桥接节点内部 + Gazebo 插件内部**。

| 话题 | 方向 | 内容 |
|---|---|---|
| /clock | Gazebo→ROS | 仿真时钟 |
| /scan | Gazebo→ROS | 激光（墙体感知靠它） |
| /odom | Gazebo→ROS | 里程计位姿 |
| /tf | Gazebo→ROS | odom→base_link |
| /joint_states | Gazebo→ROS | 轮关节状态 |
| /cmd_vel | ROS→Gazebo | Twist 速度命令 |

### 4.6 /cmd_vel 是什么（之前的疑问）
- 一个 **Topic**，消息类型 `geometry_msgs/msg/Twist`：`linear.x`=前进线速度(m/s)，`angular.z`=绕竖直轴角速度(rad/s)。
- 链路：DWB → /cmd_vel_nav → velocity_smoother → /cmd_vel → 桥接 → Gazebo DiffDrive → 轮子。
- 差速车不能横移，没有 linear.y。

### 4.7 传感器：墙体靠雷达，摄像头是关的（今天的疑问）
- **墙体/障碍感知靠激光雷达**：`robot.gazebo` 里 `gpu_lidar`，360°、720 条射线、10Hz，发 /scan。用途：① AMCL 定位匹配；② 代价地图避障。
- **摄像头传感器在 robot.gazebo 里被注释禁用**（虚拟机无 GPU 渲染不动）。打开的话 Gazebo 会虚拟渲染图像——是仿真画面，但格式是真的图像消息。所以"摄像机也是仿真的吗"→ 定义在、当前关着，迎宾走 fake 模式。

## 简历第 5 条：访客检测与迎宾

> 基于 marker 与距离阈值判定访客到位并触发迎宾播报，检测坐标与距离阈值参数化可配（默认仿真触发，另支持摄像头红色物体检测）。

### 5.1 fake 模式原理（今天的疑问起点）
- 订阅 `/odom` 存机器人位姿 → 算到预设 marker 的**欧氏距离** `math.hypot(x-mx, y-my)` → 小于 `distance_threshold`(1.2m) 触发 → 发布 `/tour_guide/visitor_detected`。
- 只在 `WAIT_VISITOR` 状态工作；触发一次后置 `_detected` 防重复。

### 5.2 marker 坐标是什么？是自己起的名字吗？（今天的疑问）
- `marker_x=1.5, marker_y=-3.5` 是**开发者自己起的变量名**，不是 ROS 术语（别和 RViz 的 Marker 可视化消息混淆）。
- 含义：**世界坐标里的一个"假访客"占位点**——机器人靠近它就当"遇到参观者"。
- 本质是 fake 方案：虚拟机里没法放真人，用坐标桩代替，**先把业务流程跑通，把真实感知解耦掉**。
- 注意：场景里 (1.5,-3.5) 有根红色立柱做视觉示意，但 fake 模式不识别它；launch 里实际配置为 (0,-3.5)。

### 5.3 "参数化"是什么意思（今天的疑问）
- 把可调数值从代码抽到参数系统：`declare_parameter("marker_x", 1.5)` 等，代码只写逻辑。
- 好处：**改触发距离、改访客位置、切 fake/camera 模式，一行代码不用改**，launch 传参即可（如 `use_fake:=false`）。
- 面试话术："业务逻辑与配置解耦，方便现场调参和适配不同场地。"

### 5.4 odom 直接比较的局限（面试加分点，今天确认）
- 仿真无轮子打滑 → **odom ≈ 世界坐标**，才能拿 /odom 直接和 marker（世界坐标）相减。
- 真机轮子打滑 → odom 漂移，直接比较不成立。真机方案：
  1. 改用 AMCL 的 map→base_link 位姿比较（推荐）；
  2. 或用 TF2 把 marker 世界坐标转到 odom 系再比。
- 面试话术："这个 fake 模式在仿真里直接用 odom 比较可行，真机上我会改用 AMCL 的 map 位姿，或通过 TF2 转换坐标系再判断。"——**主动暴露局限 = 加分**。

### 5.5 摄像头模式：识别什么？（今天的疑问）
- 识别**红色物体**，标准 OpenCV 颜色检测（不是深度学习）：
  1. `cv_bridge` 把 ROS Image 转 OpenCV 图；
  2. 转 HSV 色彩空间；
  3. 红色跨 HSV 0/180 两端，取 [0,10]∪[160,180] 两段 `inRange` 合并成掩码；
  4. 数红色像素 `countNonZero` > 500（`red_area_threshold`）即判定有访客。
- **降级设计**：cv_bridge 缺失自动退回 fake 模式。
- 当前默认 `use_fake=True`，摄像头传感器也禁用，这条路径是预留能力。

## 简历第 6 条：语音播报与问答

> 对接离线 TTS 合成讲解音频并按展点播报；实现基于关键词匹配的问答节点，问答规则与展点讲解词由 YAML 配置驱动，便于扩展新展点。

### 6.1 pyttsx3 怎么实现离线？（今天的疑问）
- 核心三行：`pyttsx3.init()` → `engine.say(text)` → `engine.runAndWait()`（阻塞等播完）。
- **为什么叫离线**：pyttsx3 不调云端接口，而是**直接调用操作系统自带的语音引擎**：
  - Linux → espeak-ng；Windows → SAPI5；macOS → NSSpeechSynthesizer
- 引擎在本地把文字转音频，**全程不需要网络**。
- **降级设计**（虚拟机常没声卡）：`init()` 失败 → 降级为日志/终端打印；播放失败 → 同样降级打印。业务不崩——"执行层可降级"的工程思路。

### 6.2 百度那种是什么？是 AI 模型吗？（今天的疑问）
**是的**，百度/讯飞是云端神经语音合成，和 pyttsx3 是两代技术：

| | pyttsx3（本项目） | 百度/讯飞云端 TTS |
|---|---|---|
| 引擎位置 | 本地系统引擎 | 云端服务器 |
| 原理 | 规则/拼接合成 | **深度学习神经语音合成（AI 模型）** |
| 联网 | 不需要（离线） | 需要：文本上传→云端合成→返回音频流 |
| 音质 | 机械音 | 接近真人、可选音色 |

- 选 pyttsx3 的理由：离线、零依赖、虚拟机能跑，符合"先跑通业务"。
- 面试话术："TTS 我用了 pyttsx3 离线方案保证不依赖网络；要更自然音质可接百度/讯飞云端神经 TTS，但需联网和额度——它是可替换的执行层。"

### 6.3 按展点播报的链路
```
tour_node 到站 → 读 tour_points.yaml 里该展点 speech
  → 发布 /tour_guide/speech → tts_node 订阅 → pyttsx3 播报
```
讲解词全在 YAML 里，**改讲解词不用改代码**。

### 6.4 问答：关键词匹配，不是大模型
- `qa_node` 收到 `/tour_guide/question` → 遍历 `qa_rules.yaml` → **关键词包含匹配**，命中第一条规则返回答案，无命中用默认回答。
- 问题来源：`voice_input_sim` 在 QA 状态等约 3s 仿真时间后随机选一个发布（**模拟提问，无真实麦克风/ASR**）。
- 面试边界：明确说"当前是规则匹配，后续可接大模型/RAG"——不夸大。

### 6.5 YAML 配置驱动，便于扩展新展点
- 加一个展点 = 在 `tour_points.yaml` 加一段（name/x/y/yaw/speech/qa_prompt），**状态机、导航、播报代码零改动**。
- 这就是简历里"便于扩展新展点"的实现依据。

## 附：面试万能应答框架（今天沉淀）
1. **边界意识**：先说"这是现成组件（Nav2/AMCL/桥接节点/插件）"，再说"我的工作是配置参数、编排 launch、写业务状态机、做降级与调优"。
2. **坐标系三件套**：map（绝对）/ odom（起点参考、会漂）/ base_link（车体），TF 缝合高低频定位。
3. **主动暴露局限**：odom 直接比较只在仿真成立，真机要换 map 位姿或 TF 转换；迎宾/提问是模拟输入，后续可接真实传感器。
4. **降级设计**：TTS 无声卡降级打印、cv_bridge 缺失降级 fake——体现工程健壮性思维。
