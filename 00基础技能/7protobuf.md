
# Protobuf 笔记（面试版）

## 1. 一句话定义

**Protobuf（Protocol Buffers）是 Google 开源的一种二进制序列化格式，用来把结构化数据编码成紧凑的二进制，用于存储或网络传输。**

它需要先写 `.proto` 文件定义数据结构，再用工具生成各语言的代码，然后通过生成的类来序列化和反序列化。

---

## 2. 核心概念

| 概念            | 说明                                                       |
| --------------- | ---------------------------------------------------------- |
| `.proto` 文件 | 定义消息结构，类似“数据结构的接口定义”                   |
| `message`     | 一条结构化数据，类似 C++ 的 struct / 类的数据部分          |
| `field`       | 消息里的字段，有类型和唯一编号                             |
| 字段编号        | 每个字段有一个数字编号，序列化时用编号代替字段名，节省空间 |
| `serialize`   | 把对象转成二进制字节流                                     |
| `parse`       | 把二进制字节流还原成对象                                   |
| 代码生成        | `protoc` 根据 `.proto` 生成 C++/Java/Python 等代码     |

示例 `.proto`：

```proto
message Person {
  string name = 1;
  int32 age = 2;
  repeated string emails = 3;
}
```

- `= 1`、`= 2`、`= 3` 是字段编号，不是值。
- 序列化后，字段名不会出现在二进制里，只出现编号和值。

---

## 3. Protobuf vs JSON 对比

| 维度            | Protobuf                   | JSON                    |
| --------------- | -------------------------- | ----------------------- |
| 格式            | 二进制                     | 文本                    |
| 可读性          | 人不可读，需要工具解析     | 人可读，直接看          |
| 体积            | 小，通常比 JSON 小 30%~70% | 大，字段名重复出现      |
| 序列化速度      | 快                         | 较慢                    |
| 反序列化速度    | 快                         | 较慢                    |
| 是否需要 schema | 需要`.proto` 文件        | 不需要，自描述          |
| 跨语言          | 支持多语言，生成代码       | 所有语言都支持          |
| 版本兼容        | 强，加字段/删字段兼容性好  | 弱，需要手动处理        |
| 调试            | 不方便，要看二进制         | 方便，直接看文本        |
| 浏览器支持      | 不直接支持，需要库         | 原生支持                |
| 可扩展性        | 字段编号管理，适合长期演进 | 字段名管理，容易冲突    |
| 典型场景        | 微服务 RPC、移动端、嵌入式 | Web API、配置文件、日志 |

---

## 4. 为什么 Protobuf 体积小、速度快？

### 体积小

- 字段名不传输，只传字段编号。
- 编号和类型打包成一个字节（tag）。
- 整数用 varint 编码，小数字占更少字节。
- 没有 JSON 那些 `{}`、`""`、`,`、`:` 符号。

### 速度快

- 二进制解析，不需要字符串解析。
- 不需要查字段名，直接按编号读。
- 生成代码直接操作内存，减少反射。

---

## 5. Protobuf 的缺点

- 不可读，调试麻烦。
- 需要 `.proto` 文件和代码生成步骤。
- 浏览器支持不好。
- 小数据量时优势不明显。
- 修改 `.proto` 要小心字段编号，不能随便复用。
- 不适合做配置文件给人看。

---

## 6. 什么时候用 Protobuf，什么时候用 JSON？

### 用 Protobuf

- 微服务之间 RPC 通信（gRPC 默认用 Protobuf）。
- 移动端和服务器通信，省流量。
- 嵌入式设备，资源受限。
- 数据量大、性能要求高。
- 需要长期演进的接口，字段经常增删。

### 用 JSON

- Web 前端和后端交互。
- 配置文件，人要读要改。
- 日志、调试信息。
- 对外公开 API，方便第三方接入。
- 数据量小，性能要求不高。

---

## 7. 面试常见问题与回答

### Q1：Protobuf 和 JSON 有什么区别？

**答**：Protobuf 是二进制格式，需要 `.proto` 定义结构，体积小、速度快，但不可读；JSON 是文本格式，自描述、可读性好，但体积大、速度慢。Protobuf 适合高性能 RPC 和移动端，JSON 适合 Web API 和配置文件。

### Q2：Protobuf 为什么快？

**答**：因为它用二进制编码，字段名不传输，只传字段编号；整数用 varint 压缩；解析时不需要字符串匹配，直接按编号读；生成代码直接操作内存。

### Q3：Protobuf 的字段编号有什么用？

**答**：字段编号是字段在二进制里的唯一标识。序列化时只传编号和值，不传字段名。编号一旦使用就不能随意更改或复用，否则会导致新旧版本不兼容。

### Q4：Protobuf 怎么保证版本兼容？

**答**：

- 新增字段用新编号，旧代码会忽略不认识的字段。
- 删除字段时保留编号，不要复用。
- 不要修改已有字段的编号和类型。
- 可选字段和默认值处理得当，就能向前向后兼容。

### Q5：Protobuf 和 gRPC 什么关系？

**答**：gRPC 是 Google 的 RPC 框架，默认用 Protobuf 作为接口定义语言和序列化格式。`.proto` 文件里既定义消息，也定义服务方法，gRPC 根据它生成客户端和服务端代码。

### Q6：Protobuf 能不能直接用在浏览器？

**答**：不能直接像 JSON 那样用。浏览器原生不支持 Protobuf，需要引入 protobuf.js 之类的库，或者用 gRPC-Web。所以 Web 前端通常还是用 JSON。

### Q7：Protobuf 的 `repeated` 和 JSON 数组有什么区别？

**答**：`repeated` 表示字段可以出现多次，类似数组。Protobuf 里 repeated 字段可以打包编码，更省空间。JSON 数组就是普通数组，每个元素都要完整写出来。

### Q8：Protobuf 的 `optional` 和 `required` 呢？

**答**：Proto2 有 `required`、`optional`、`repeated`。Proto3 默认都是 optional，去掉了 `required`，因为 `required` 容易导致兼容性问题。现在推荐用 `optional` 显式标记可选字段。

---

## 8. 一句话面试总结

> Protobuf 是二进制序列化格式，靠 `.proto` 定义结构，字段编号代替字段名，体积小、速度快、跨语言、兼容性好，适合 RPC 和移动端；JSON 是文本格式，可读性好、无需 schema，适合 Web API 和配置文件。两者不是替代关系，而是不同场景用不同工具。

---

## 9. 记忆口诀

- **Protobuf**：二进制、有 schema、小快、难读、RPC 首选。
- **JSON**：文本、无 schema、大慢、易读、Web 首选。
- **选型**：性能敏感用 Protobuf，可读性优先用 JSON。
