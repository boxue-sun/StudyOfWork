## 一、停止线穿越检测算法

### 1.1 这个模块是干什么的？

交通流统计的核心事件是"车辆过线"。只有车辆穿过停止线，才计入流量。停止线穿越检测器（StopLineCrossingTracker）负责判断每一帧中哪些车辆完成了过线动作，返回过线车辆列表，供下游的车流量检测器、车头时距检测器使用。

### 1.2 为什么不只看单帧位置，必须用跨帧检测？

单帧只能知道"车在线上"，但无法判断方向：

- 车可能停在线上等红灯
- 车可能从对面驶来还没过线
- 只有看到**连续两帧的位置变化**，才能确定车辆是从停止线后方穿到前方

所以必须用"上一帧位置 → 当前帧位置"连成的**位移线段**与停止线做几何相交判断。

### 1.3 具体算法是什么？

```
对于每一帧中的每辆车：
1. 取出该车辆上一帧的位置 prev_pos（缓存在 _prev_positions map 中）
2. 取出当前帧位置 curr_pos
3. 用 prev_pos 和 curr_pos 构造一条位移线段 movement
4. 判断 movement 是否与停止线 _stop_line 相交
5. 如果相交且该车尚未被记录为已穿越（防止重复计数），则：
   - 加入 _crossed_ids 集合
   - 加入返回列表 crossed
6. 更新 _prev_positions[obj.id] = curr_pos
```

### 1.4 线段相交判断的数学原理是什么？

用的是**参数化线段方程 + 求解交点**的方法。

设线段 A（停止线）从 P1 到 P2，线段 B（车辆位移）从 P3 到 P4。

用参数方程表示：

- 线段 A 上的点：P1 + r × (P2 - P1)，r ∈ [0, 1]
- 线段 B 上的点：P3 + s × (P4 - P3)，s ∈ [0, 1]

联立方程求解 r 和 s：

- 如果 d ≠ 0（两线段不平行），计算 r 和 s
- 如果 r ∈ [0, 1] 且 s ∈ [0, 1]，说明两条线段在各自的有效范围内相交

代码实现（segment2d.hpp 的 has_intersect 方法）：

```cpp
double d = (x2-x1)*(y4-y3) - (y2-y1)*(x4-x3);  // 叉积分母
if (d != 0) {
    double r = ((y1-y3)*(x4-x3) - (x1-x3)*(y4-y3)) / d;
    double s = ((y1-y3)*(x2-x1) - (x1-x3)*(y2-y1)) / d;
    if (r >= 0 && r <= 1 && s >= 0 && s <= 1) {
        return true;  // 相交
    }
}
```

**面试话术**：用叉积判断两条线段是否相交。把车辆两帧位置连成线段，与停止线线段求交点参数，两个参数都在 [0,1] 范围内说明在有效线段内相交。

### 1.5 为什么用 map 和 set 做缓存？

| 数据结构                                    | 用途                   | 为什么选它                       |
| ------------------------------------------- | ---------------------- | -------------------------------- |
| `std::map<string, Vec2D> _prev_positions` | 缓存每辆车上一帧的位置 | 需要通过车辆 ID 快速查找和更新   |
| `std::set<string> _crossed_ids`           | 记录已经过线的车辆 ID  | 防止同一辆车在后续帧中被重复计数 |

**面试追问：为什么不用 unordered_map？**

- map 基于红黑树，O(log n) 查找；unordered_map 基于哈希表，O(1) 查找
- 这里用 map 是因为车辆数量通常不大（几十辆），性能差异可忽略
- 如果面试官追问，可以说"如果车辆数量很大，可以换成 unordered_map 提升性能"

### 1.6 首次出现的车辆为什么检测不到？

因为 `_prev_positions` 中没有这辆车的记录，代码走不进 `if (prev_it != _prev_positions.end())` 分支，无法构造位移线段。

**这是正确的设计**：必须至少观察两帧才能确定运动方向，单帧无法判断过线。

### 1.7 reset() 和 clear_crossing_state() 的区别？

| 方法                       | 清除内容                            | 使用场景                                       |
| -------------------------- | ----------------------------------- | ---------------------------------------------- |
| `reset()`                | 清除 _prev_positions + _crossed_ids | 统计周期结束，完全重置                         |
| `clear_crossing_state()` | 只清除 _crossed_ids                 | 保留位置缓存，只重置穿越状态（如信号灯切换时） |

## 二、信号灯相位边界检测

### 2.1 这个模块是干什么的？

接收 TLP（Traffic Light Preprocess）模块发布的信号灯 JSON 数据，维护每个 phase 的当前灯态，检测"绿→红→绿"的相位边界变化，用于触发对应方向的流量统计窗口重置。

**为什么需要这个？**

- 交通流统计需要按信号灯周期来切分窗口
- 每次绿灯亮起时，重置计数器，开始新一轮统计
- 这样输出的数据粒度是"每个信号周期"，对自动驾驶车辆更有参考价值

### 2.2 整体数据流是怎样的？

```
TLP 模块（DDS 发布）
    ↓ on_data_available() 回调（DDS 通信线程）
SignalPhaseManager::on_signal_data(json)
    ↓ 加锁写入 _phase_states
detect() 主循环（工作线程）
    ↓ 调用 check_and_consume_cycle_boundary()
    ↓ 如果检测到绿→红→绿边界，返回 true
TrafficFlowFactory
    ↓ 触发对应方向检测器的 reset()
    ↓ 开始新一轮统计
```

### 2.3 SignalPhaseManager 的核心设计

**单例模式 + mutex 保护**：

- DDS 回调线程写数据，工作线程读数据 → 必须线程安全
- 用 `std::mutex` + `std::lock_guard`（RAII 模式）保证互斥访问

```cpp
void SignalPhaseManager::on_signal_data(const nlohmann::json& signal_json) {
    std::lock_guard<std::mutex> lock(_mutex);  // RAII 自动加锁解锁
    // 解析 JSON，更新 _phase_states[phase_id] = light
    // 检测参考相位的绿→红→绿边界
}
```

### 2.4 相位边界检测的具体逻辑

```cpp
// 在 on_signal_data() 中，对参考相位做边界检测：
bool now_green = (light == LIGHT_PERMISSIVE_GREEN || light == LIGHT_PROTECTED_GREEN);
bool was_green = (_prev_reference_light == LIGHT_PERMISSIVE_GREEN || 
                  _prev_reference_light == LIGHT_PROTECTED_GREEN);

// 当前是绿灯，之前不是绿灯，且之前有有效数据（非初始状态 0）
if (now_green && !was_green && _prev_reference_light != 0) {
    _cycle_boundary = true;  // 标记发生了相位边界
}
```

**为什么需要 `_prev_reference_light != 0` 这个条件？**

- 初始状态下 `_prev_reference_light = 0`，表示还没有收到过数据
- 如果去掉这个判断，第一次收到绿灯数据时就会误触发边界检测
- 必须等到有了"之前不是绿灯"的真实数据后，才能判断"现在变绿了"是真正的相位切换

### 2.5 check_and_consume_cycle_boundary() 为什么叫"consume"？

```cpp
bool SignalPhaseManager::check_and_consume_cycle_boundary() {
    std::lock_guard<std::mutex> lock(_mutex);
    if (_cycle_boundary) {
        _cycle_boundary = false;  // 消费掉，只返回一次 true
        return true;
    }
    return false;
}
```

这是一个**生产者-消费者模式**的变体：

- `on_signal_data()` 是生产者，设置 `_cycle_boundary = true`
- `check_and_consume_cycle_boundary()` 是消费者，读取后立即清零
- 保证每个边界事件只被处理一次，不会重复触发 reset

**面试话术**：我用了一个标志位 + 消费语义的设计。DDS 回调线程检测到相位边界时设置标志，工作线程每次循环检查并消费这个标志，读到 true 后立即清零，保证每个信号周期只触发一次统计重置。

### 2.6 信号灯状态枚举

```cpp
constexpr int LIGHT_RED = 3;              // 红灯
constexpr int LIGHT_PERMISSIVE_GREEN = 5; // 许可绿灯（可转弯）
constexpr int LIGHT_PROTECTED_GREEN = 6;  // 保护绿灯（直行优先）
constexpr int LIGHT_YELLOW = 7;           // 黄灯
```

**为什么绿灯分两种？**

- 许可绿灯（permissive green）：允许通行但需让行，比如左转绿灯但要让对向直行
- 保护绿灯（protected green）：独占通行权，对向全部红灯
- 交通流统计中两种绿灯都算"可通行"，所以 is_green() 判断时两个都算

### 2.7 线程安全是怎么保证的？

| 场景                         | 保护机制                                                  |
| ---------------------------- | --------------------------------------------------------- |
| DDS 回调线程写 _phase_states | `std::lock_guard<std::mutex>`                           |
| 工作线程读 _phase_states     | `std::lock_guard<std::mutex>`（is_green 方法）          |
| 工作线程消费 _cycle_boundary | `std::lock_guard<std::mutex>`（check_and_consume 方法） |

**为什么用 lock_guard 而不是手动 lock/unlock？**

- RAII 思想：lock_guard 构造时自动加锁，析构时自动解锁
- 即使中间抛出异常，也能保证锁被正确释放，避免死锁
- 手动 lock/unlock 容易忘记在某个 return 路径上解锁

**面试追问：为什么不用读写锁 shared_mutex？**

- 当前场景写操作很少（只有 on_signal_data 写），读操作也很轻量
- shared_mutex 适合读多写少的场景，这里读写都很频繁且轻量，普通 mutex 足够
- 如果未来性能成为瓶颈，可以考虑换成 shared_mutex 优化读性能

## 三、DDS 通信层

### 3.1 DDS 是什么？

DDS（Data Distribution Service）是一种分布式发布-订阅通信中间件，用于实时系统。

**核心概念**：

| 概念       | 说明                              | 类比             |
| ---------- | --------------------------------- | ---------------- |
| Topic      | 数据主题，定义数据类型            | 微信的聊天频道   |
| Publisher  | 数据发布者                        | 发消息的人       |
| Subscriber | 数据订阅者                        | 收消息的人       |
| PartId     | 参与者标识，区分不同的 Topic 实例 | 不同的聊天群号   |
| Domain     | 逻辑隔离域                        | 不同的微信服务器 |

**为什么用 DDS 而不是 TCP/UDP？**

- DDS 内置了服务发现、数据序列化、QoS 策略
- 发布者和订阅者无需知道对方地址，自动发现
- 支持实时性保证（适合交通场景的低延迟需求）

### 3.2 项目中的 DDS 双数据流架构

```
┌─────────────────────────────────────────────────────┐
│                  DDS 通信层                          │
│                                                     │
│  RSM_JSON_SUB (id=0)     SIGNAL_JSON_SUB (id=2)    │
│  感知数据订阅              信号灯数据订阅              │
│       ↓                          ↓                  │
│  BlockingQueue            SignalPhaseManager         │
│  (无锁队列缓存)            (线程安全状态缓存)          │
│       ↓                          ↓                  │
│  ┌──────────────────────────────────────┐           │
│  │         detect() 主循环               │           │
│  │    （工作线程，周期性执行）              │           │
│  │                                      │           │
│  │  1. 从 BlockingQueue 取感知数据       │           │
│  │  2. 检查 SignalPhaseManager 边界     │           │
│  │  3. 驱动检测器管道运行                │           │
│  │  4. 输出统计结果                     │           │
│  └──────────────────────────────────────┘           │
│                      ↓                              │
│         TRAFFIC_FLOW_JSON_PUB (id=1)                │
│         交通流统计结果发布                             │
└─────────────────────────────────────────────────────┘
```

### 3.3 PartId 枚举设计

```cpp
enum class PartId : uint8_t {
    RSM_JSON_SUB = 0,          // 感知数据订阅
    TRAFFIC_FLOW_JSON_PUB = 1, // 交通流结果发布
    SIGNAL_JSON_SUB = 2,       // 信号灯数据订阅
    QUALITY_JSON_PUB = 253,    // 质量监控发布
    PART_ID_STATE_JSON_PUB = 254,
    PART_ID_LOG_JSON_PUB = 255
};
```

**为什么用 enum class 而不是普通 enum？**

- enum class 有强类型检查，不会隐式转换为 int
- 有独立的作用域，不会污染命名空间
- 防止不同枚举之间的意外比较

**面试话术**：我用 enum class 定义了 PartId，每个值对应一个 DDS Topic 实例。enum class 相比传统 enum 有类型安全和作用域隔离的优势，避免了隐式类型转换和命名冲突。

### 3.4 on_data_available() 回调机制

```cpp
void TrafficFlowServiceImpl::on_data_available(uint8_t id, const void* message) {
    const FusionMsg* fusion_message = static_cast<const FusionMsg*>(message);
    PartId message_type = static_cast<PartId>(id);
  
    switch (message_type) {
        case PartId::RSM_JSON_SUB: {
            // 感知数据 → 放入 BlockingQueue → 工作线程消费
            traffic_flow_factory.update_new_frame(contents);
            break;
        }
        case PartId::SIGNAL_JSON_SUB: {
            // 信号灯数据 → 解析 JSON → 更新 SignalPhaseManager
            nlohmann::json signal_json = nlohmann::json::parse(contents);
            traffic_flow_factory.on_signal_data(signal_json);
            break;
        }
        default:
            break;
    }
}
```

**为什么两条数据流的处理方式不同？**

- 感知数据：频率高（每帧都有），放入 BlockingQueue 缓冲，工作线程按自己的节奏消费
- 信号灯数据：频率低，状态变化少，直接更新到 SignalPhaseManager 的缓存中，工作线程轮询检查

**设计考量**：

- 感知数据用 BlockingQueue 是因为处理耗时，不能在回调线程中阻塞
- 信号灯数据直接更新缓存是因为数据量小、处理快，且需要保持状态连续性

### 3.5 BlockingQueue 的作用

```
DDS 回调线程（生产者）
    ↓ 每帧调用 update_new_frame()
    ↓ 将 JSON 字符串推入队列
BlockingQueue
    ↓ 线程安全的无锁/有锁队列
    ↓ 缓冲突发数据
detect() 工作线程（消费者）
    ↓ 循环从队列取数据
    ↓ 处理感知数据
```

**为什么需要 BlockingQueue？**

- DDS 回调线程不能阻塞（会影响其他 Topic 的接收）
- 检测器处理一帧数据可能需要几十毫秒
- BlockingQueue 解耦了数据接收和数据处理，允许两者以不同速度运行

### 3.6 插件化架构设计

项目构建产物是 `libTrafficFlowService.so`（共享库），不是独立可执行文件。

**为什么设计成插件？**

- 宿主框架 FusionService 统一管理多个感知模块
- 每个模块独立编译、独立部署、独立升级
- 宿主框架负责 DDS 初始化、生命周期管理、日志输出

**插件与宿主的交互**：

```cpp
// 宿主框架通过函数指针提供 API
const FSTrafficFlowService* s_fs_api_;
s_fs_api_->TrafficFlowService_Publish(...)   // 发布数据
s_fs_api_->TrafficFlowService_Log(...)       // 输出日志
```

## 四、高频面试 Q&A

### Q1: 你的项目解决了什么问题？

**A**: 我负责的是路侧协同感知系统中的交通流实时统计模块。部署在路侧 MEU 设备上，实时接收视频感知数据和信号灯数据，按车道级粒度统计车流量、排队长度、车头时距等指标，通过 DDS 发布给自动驾驶车辆消费。

### Q2: 停止线穿越检测的算法复杂度是多少？

**A**: 每帧处理复杂度是 O(N × log M)，其中 N 是当前帧车辆数，M 是缓存的历史车辆数。map 查找是 O(log M)，线段相交判断是 O(1)。总体是线性复杂度，满足实时性要求。

### Q3: 如果车辆 ID 不稳定怎么办？

**A**: 这是实际场景中的常见问题。如果感知模块的跟踪算法不稳定，同一辆车可能被分配不同 ID，导致：

- 位移线段断裂，无法检测到过线
- 解决方案是引入时间窗口，如果一辆车消失后短时间内在停止线附近出现新车，可以认为是同一辆车

### Q4: 信号灯数据为什么用被动订阅而不是主动拉取？

**A**: 主动拉取会引入轮询延迟和资源浪费。被动订阅模式下，TLP 模块每次状态变化都会主动推送，我们能第一时间感知到相位切换，保证流量统计窗口的精确性。

### Q5: 多线程安全你是怎么考虑的？

**A**: 主要用 mutex + lock_guard 保护共享状态。SignalPhaseManager 被 DDS 回调线程和工作线程同时访问，所有读写操作都通过 lock_guard 加锁。用 RAII 模式管理锁的生命周期，即使发生异常也能保证锁被正确释放。

### Q6: 为什么选择 DDS 而不是其他通信方式？

**A**: DDS 是实时系统的标准通信中间件，有几个优势：

1. 内置服务发现，发布者和订阅者无需硬编码地址
2. 支持 QoS 策略，可以配置可靠性、实时性等参数
3. 数据序列化透明，无需手动编解码
4. 在自动驾驶和工业控制领域有广泛应用，生态成熟

### Q7: 如果信号灯数据丢失了怎么办？

**A**: 当前实现没有显式的超时检测机制。如果 TLP 模块停止发布数据，SignalPhaseManager 会保持最后一次的状态。改进方案是增加心跳检测，如果超过一定时间没收到数据，标记为"信号灯离线"，下游检测器切换到无信号灯模式。

### Q8: 检测器管道是怎么设计的？

**A**: 采用配置驱动的插件化架构。TrafficFlowFactory 读取 JSON 配置，根据 detector_cycles 字段动态创建检测器实例。支持两种检测模式：

- Snapshot（秒级快照）：每帧 compute()，1s 到点时聚合输出并 reset()
- Accumulate（5分钟累积）：每帧 update()，5min 到点时 calculate_once() 输出并清零

新增检测器类型只需继承基类、实现虚函数、在工厂中添加创建逻辑，无需修改调度代码。

## 六、面试话术模板

### 介绍项目（30秒版）

> 我参与的是路侧协同感知项目，负责交通流实时统计模块。系统部署在路侧设备，通过 DDS 接收视频感知和信号灯数据，按车道级粒度统计车流量、排队长度、车头时距等指标，输出给自动驾驶车辆。我主要负责停止线穿越检测算法和信号灯相位边界检测模块的设计与实现。

### 深入讲停止线穿越（2分钟版）

> 停止线穿越检测的核心是判断车辆是否穿过停止线。我用的是跨帧几何相交算法：把每辆车上一帧和当前帧的位置连成一条位移线段，判断这条线段是否与停止线相交。具体实现用参数化线段方程求解交点参数，两个参数都在 [0,1] 范围内说明在有效线段内相交。
>
> 为什么必须用跨帧？因为单帧只能知道车在线上，无法判断方向。必须看到连续两帧的位置变化，才能确定车辆是从停止线后方穿到前方。
>
> 实现上用 map 缓存每辆车的上一帧位置，用 set 记录已过线的车辆防止重复计数。首次出现的车辆因为没有历史位置，无法触发检测，这是正确的设计——必须至少观察两帧才能确定运动方向。

### 深入讲信号灯相位边界（2分钟版）

> 信号灯相位边界检测用于识别信号周期的切换点。我设计了 SignalPhaseManager，通过 DDS 被动订阅 TLP 模块的信号灯数据，用 mutex + lock_guard 保证线程安全。
>
> 核心逻辑是检测参考相位的"绿→红→绿"边界变化。DDS 回调线程更新灯态缓存，工作线程通过 check_and_consume_cycle_boundary() 消费边界事件。这个方法用了生产者-消费者模式的变体，读到 true 后立即清零，保证每个信号周期只触发一次统计重置。
>
> 为什么用被动订阅而不是主动拉取？因为被动订阅能第一时间感知相位切换，保证流量统计窗口的精确性。主动拉取会引入轮询延迟。

## 七、常见追问及应对

### 面试官问：这个算法有什么改进空间？

**回答方向**：

1. 引入卡尔曼滤波预测车辆轨迹，减少感知噪声影响
2. 增加车辆 ID 稳定性检测，处理跟踪丢失场景
3. 用空间索引（如 R-tree）加速相交判断，支持多停止线场景

### 面试官问：如果数据量很大，性能瓶颈在哪？

**回答方向**：

1. map 查找可以换成 unordered_map，O(log n) → O(1)
2. 线段相交判断可以加 AABB 包围盒预过滤，减少不必要的精确计算
3. 多线程场景下可以考虑用无锁队列替代 BlockingQueue

### 面试官问：你遇到过什么难点？

**回答方向**：

1. 跨帧追踪的首次出现车辆问题：通过构造 mock 数据测试发现，单帧无法触发检测，必须保证每辆车至少在两帧中出现
2. 信号灯边界误触发：初始状态下 _prev_reference_light = 0，第一次收到绿灯会误触发，加了 `_prev_reference_light != 0` 条件解决
3. 线程安全问题：DDS 回调线程和工作线程同时访问 SignalPhaseManager，用 mutex 保护所有共享状态
