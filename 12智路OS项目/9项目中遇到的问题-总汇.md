## 一、部署工具 relayDeployTool（Python / paramiko / SFTP）✅ 我修的

> 一个批量部署脚本：读工参表 → SSH 连设备 → SFTP 上传配置文件。这 5 个 bug 都是我开发部署功能时实际踩到并修掉的，**是最能当「真实 bug」讲的素材**。

### Bug 1：Windows 路径分隔符导致 SFTP 上传失败（静默失败）

- **现象**：界面显示「重启中继模块成功」，但目标机器上根本没有文件。
- **原因**：用 `os.path.join()` 拼远程路径，Windows 上会生成反斜杠 `\`，拼出 `/work/sunboxue/config\work_param_config.flag` 这种混合路径，Linux SFTP 识别不了，文件上传到了错误位置或静默失败。
- **修复**：远程路径一律用正斜杠 `remote_dir.rstrip("/") + "/" + 文件名`，不用 `os.path.join`。
- **教训**：远程路径必须固定正斜杠，`os.path.join` 会随操作系统变。
- ✅ **面试一句话**：跨平台脚本里，Linux 端的路径不能用 `os.path.join` 拼，Windows 会生成反斜杠导致 SFTP 静默失败，我改成手工用正斜杠拼接。

### Bug 2：远程目录不存在导致传输失败

- **现象**：部署显示「传输文件异常」，目标机器上没有目标目录。
- **原因**：测试机不是标准 AIROS 系统，没预建目录结构，`sftp.put()` 写进不存在的目录会抛异常。
- **修复**：上传前先 `sftp.stat` 检查，不存在就递归创建（自己实现了一个类似 `mkdir -p` 的方法）。
- ✅ **面试一句话**：SFTP 上传前要先保证远程目录存在，不能假设目标机器有标准目录结构，我加了递归建目录的逻辑。

### Bug 3：基类只传核心列，子类拿不到完整行数据

- **现象**：子类只能拿到 5 个核心列（IP/路口/用户名/密码/Sn），访问不到 Excel 里的证书路径列。
- **原因**：基类在批量下发时只提取了 SSH 连接需要的列传给子类。
- **修复**：改成把完整的那一行数据传给子类。
- ✅ **面试一句话**：这是基类设计缺陷——只传了连接需要的字段，子类要扩展字段时拿不到，改成传完整行，子类就能各取所需。

### Bug 4：远程部署目录硬编码为全局常量

- **现象**：所有设备的配置文件都上传到同一个全局目录，没法给不同设备指定不同目录。
- **原因**：远程目录写死在全局常量里。
- **修复**：在工参表加「远程配置目录」列，数据结构加字段，优先用设备自己的目录，没有才退回全局默认。
- ✅ **面试一句话**：每台设备的部署路径可能不一样，我把它从全局写死改成从工参表动态指定，设备优先用自己的配置。

### Bug 5：SSH 连接和传输日志不够详细

- **现象**：部署失败时只显示「传输文件异常」，看不到具体原因，很难排查。
- **原因**：异常信息被截断，SSH 连接日志缺失。
- **修复**：SSH 连接前后都打日志，异常信息带上类型名（`type(e).__name__`）。
- ✅ **面试一句话**：网络操作必须记好连接前后的日志，异常信息要带类型名，否则线上出问题没法排查。

## 二、GPU 监控功能（C++ / CUDA / Docker / Linux）✅ 我做的

> 给 MonitorService 监控服务加 GPU 频率 + 显存采集。最大的价值在「数据不准 → 怎么定位 → 怎么改对」这条排查链。

### 问题 1：CUDA API 读出来的显存不准（偏大 30 倍）

- **现象**：用 `cudaMemGetInfo()` 读显存，得到 ~6900MB，但 jtop 工具显示真实只用了 ~218MB。
- **原因**：Jetson 是 CPU/GPU 统一内存架构，`cudaMemGetInfo` 返回的是 CUDA 运行时内存池信息，包含了 context、驱动预留、内存池碎片，不是真实进程占用。
- **解决**：改读 NVIDIA 驱动接口 `/sys/kernel/debug/nvmap/iovmm/maps` 的 `total` 行（jtop 同款数据源），显存从 6.9GB 修正到真实 ~218MB。
- ✅ **面试一句话**：我发现 CUDA 的显存接口读出来虚高 30 倍，对比官方工具后改用 nvmap 驱动接口，把误差从 6.9GB 修到真实 218MB。

### 问题 2：Docker 容器里访问不到 debugfs

- **现象**：代码在宿主机正常，进容器后 GPU 显存就降级走了 CUDA 分支。
- **原因**：Docker 容器有独立的文件系统视图，`/sys/kernel/debug`（debugfs）**默认不挂载，即使加 `--privileged` 也不会自动挂**。
- **解决**：容器启动脚本里显式挂载 `-v /sys/kernel/debug:/sys/kernel/debug:ro`。
- ✅ **面试一句话**：`--privileged` 不是万能的，内核调试接口 debugfs 必须显式 `-v` 挂载进容器。

### 问题 3：容器里 sudo 报错 + 错误被吞

- **现象**：挂载后用 `sudo cat` 读还是失败，而且报错被 `2>/dev/null` 吞了，很隐蔽。
- **原因**：容器里 sudo 插件（`sudoers.so`）权限被破坏（`must be owned by uid 0`）；而且挂载后普通 `cat` 本来就能读，根本不需要 sudo。
- **解决**：代码改用普通 `cat`，去掉 sudo；调试时先去掉 `2>/dev/null` 让错误露出来。
- ✅ **面试一句话**：容器里别依赖 sudo（权限容易被破坏），挂载后普通权限就能读；`2>/dev/null` 会把错误吞掉，排查时要先去掉。

### 问题 4：GPU 空闲时温度是 -256℃ 无效值

- **现象**：日志报 `get gpu-info failure!`，GPU 数据采不到。
- **原因**：GPU 空闲时温度传感器返回 -256℃（无效值），采集函数判断 `temp >= 0` 才有效，所以整体失败。
- **解决**：在宿主机跑 GPU 负载让温度升回 ~40℃，读数恢复正常。
- ✅ **面试一句话**：GPU 空闲时温度传感器会返回无效值（-256℃），导致采集判定失败，我通过跑负载复现并确认了这是传感器在空闲态的读数特性。

### 附带的设计：三级降级容错

- nvmap 读成功 → 返回准确值；失败 → 降级 CUDA API（偏大但有值）；再失败 → 返回 -1 标记无效。
- 原则：**监控服务宁可给个不太准的值，也不能没有值**。
- ✅ **面试一句话**：监控采集做了三级降级，优先准确的数据源，读不到就退回备用的、再退回无效标记，保证服务不中断。

## 四、AirOS 多路视频接入（C++ / FFmpeg）⚠️ 参与搭建（现有设计）

- **问题**：相机断流以后，采集要能自己恢复。
- **设计**：双层循环——外层负责连接，内层负责持续读包；内层读失败就跳出，关掉旧连接，sleep 后再重新连；每路流又是独立线程，互不阻塞。
- **要点**：把「正常采集」和「异常恢复」接起来，不用每次断流都手动重启模块。
- ⚠️ **诚实口径**：这是现有重连设计（我参与搭建/理解），**不是说「我发现代码原来不重连、我修好了重连」**。停止标志不能自动打断阻塞读包，可靠退出也不能说已经验证完善。
- ✅ **面试一句话**：多路视频接入里要处理断流恢复，我用双层循环——内层读包失败就退出来，外层关连接、等一会再重连，每路流独立线程，互不影响。

## 五、交通流量模块 traffic_flow（C++ / Fast-DDS）

### 问题 1：所有目标加起来 ≠ 机动车总流量 🔴 团队历史修复

- **现象**：把行人、非机动车、机动车数量都加在一起当「机动车总流量」，类型分类里还把自行车、三轮车放进了机动车集合。程序能跑，但结果含义错了。
- **修复**：修正类型分类，机动车总量只加机动车那几类，行人/非机动车保留在各自明细；现在实现是分车型累积、到点再汇总。
- 🔴 **诚实口径**：这是**项目历史里别人修的**（不是我的提交），面试只能说「我了解这个统计口径的坑」，**不能说是我修的**。能借题发挥的是：「做统计要先弄清每个字段到底统计谁，不能觉得都是数量就直接相加」。
- ✅ **面试一句话**：统计里最容易出的是口径错——把不同车型的数量直接相加当总流量，含义就错了；正确做法是先分车型累积、到点再汇总，机动车总量只算机动车那几类。

### 问题 2：目标在线附近反复跨线 → 误计 + 重复计数 ⚠️ 参与搭建

- **现象**：同一目标会连续多帧出现，也可能在停止线附近来回抖动，看到在线附近就加一次会重复计。
- **设计**：按目标 id 存上次位置，把前后位置连成线段判断和停止线是否相交；确认过线后记录 id，同周期内不重复计；对行人/非机动车再加位移 + 横穿方向检查过滤抖动。
- ⚠️ **诚实口径**：这是现有防误计设计，**别编成「线上曾经大量误计、我修复了」**。机动车跳过严格质量门控，不能说所有车都必须移动半米。
- ✅ **面试一句话**：过线统计要防误计和重复计数，我用「前后两帧连线 + 几何相交判断」确认过线，再按 id 在周期内去重，行人非机动车再加位移和方向门控过滤抖动。

### 问题 3：上游持续来数据，接收回调不能被计算占住 ⚠️ 参与搭建

- **现象**：上游数据一直来，检测计算也需要时间，直接在接收回调里算完会占住接收线程。
- **设计**：接收和计算拆开——回调只把 JSON 解析成一帧放进**有界阻塞队列**，独立工作线程再取出来交给检测器；队列空时消费者等待，满时丢掉最老一帧，避免积压扩大。
- ⚠️ **诚实口径**：现有生产者-消费者设计，**别编成「原来积压几万帧、优化后提升多少倍」**。满时不等待空位但仍要拿锁；丢帧也会影响精度，不能说完全没代价。
- ✅ **面试一句话**：接收和计算要解耦，回调只负责解析入队，独立线程负责消费计算，用有界阻塞队列衔接，满了丢最老的一帧，避免积压。

## 六、C++ 语言层面 ✅ 学习记录

- **问题**：`const` 修饰的成员函数里不能修改成员变量，改了会编译报错。
- **解决**：确需在 const 函数里改的成员，用 `mutable` 修饰。
- ✅ **面试一句话**：const 成员函数保证不修改对象状态，个别需要改的成员（比如缓存）用 mutable 声明，明确它是「可变的例外」。
